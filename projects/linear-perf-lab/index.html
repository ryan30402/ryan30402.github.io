01 / The engineering question

Can shape predict latency?

Given matrix dimensions M, N, K, how accurately can a model predict the time required for a dense linear operation on a fixed GPU? This project compares simple compute-based estimates with shape-aware models, then checks where the predictions break down.

The central finding

Stable measurements do not guarantee the best model choice.

All six sessions passed their recorded timing gates. Yet the development-selected model did not consistently have the lowest held-out error. The frozen selections remain visible alongside all five candidates.

03 / How the study works

From timing to a testable claim.

01 / MEASURE

Fix the timing contract.

Preallocated tensors, warm reuse, and CUDA events around a captured graph with 50 GEMMs. Take 9 replay samples per visit, across 3 blocks.

02 / FIT

Compare five models.

FLOP-only, 2p and 3p Roofline, shape-log Ridge, and Roofline residual KRR. Each starts from the same 24 calibration shapes.

03 / FREEZE

Keep held-out data held out.

Select using 12 development shapes. Freeze models and predictions before collecting test and challenge labels; do not reselect after seeing them.

04 / AUDIT

Retain the evidence.

Preserve raw timing blocks, control checks, provenance hashes, frozen predictions, and numerical witnesses for later review.

Measurement contract · conceptual pseudocode
# Captured once; tensors are preallocated.
# One replay contains 50 dense matrix multiplies.
start.record()
graph.replay()
end.record()
end.synchronize()

per_gemm_us = start.elapsed_time(end) * 1000 / 50

# Main label: median of 3 block medians.
# Each block visit contains 9 replay samples.

A deliberately narrow target.

The measured time includes GPU memory accesses and replay/inter-kernel gaps. It excludes CPU↔GPU transfers, allocation, graph capture, and serving queues.

The operation has no bias or activation. These measurements are not full Transformer or end-to-end LLM latency.

The protocol contains 96 modeling/pool shapes plus 8 separate diagnostic shapes. Diagnostics are not used for model fitting or selection.

04 / Results with boundaries

What the evidence supports.

The archive preserves both useful results and reasons to be cautious.

Timing quality

Six recorded audit passes.

Recorded acquisition reviews contain 5,468 internal checks per session. BF16 s03 retains a visible control qualification: x03 spans 17.24% from its minimum, with max/min = 1.1724 under a 1.2 gate. That variation remains in the published evidence.

These are archived internal audit outcomes, not vendor certification or an independent hardware attestation.

Prediction quality

Selection is still a limitation.

Residual KRR test median APE spans 16.56–17.18% for FP16 and 16.44–16.75% for BF16. But it was selected in only one of the six sessions.

This candidate comparison does not establish that the automatic selector reliably chooses the best model or that a future redesign will improve accuracy.

Offline batching diagnostic

25.57–26.72× elapsed-time ratio.

Across the six runs, 64 small GEMMs took that much longer than one equal-work larger GEMM under the offline experiment contract.

This is not an end-to-end LLM speedup. Batching queues, CPU overhead, and serving latency are outside this comparison.

Scope and limitations

One hardware/software configuration. All sessions use NVIDIA A100-SXM4-40GB, recorded PyTorch 2.11.0+cu128, and CUDA runtime 12.8. Three recorded GPU identities do not establish cross-architecture generalization.

Repeated shapes, not independent new tests. The same 96 shapes recur in every session. Challenge families are excluded from this study's calibration, development, and acquisition sets. Future model changes require a new unseen evaluation set for a fresh generalization claim.

No mechanism claim. The package does not provide hardware counters sufficient to prove cache, bandwidth, or Tensor Core causes for a latency difference.

Reported measurements, not a browser benchmark. Changing the controls only filters archived data. No GPU work, new model fitting, or result selection runs in the browser.
